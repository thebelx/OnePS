OnePS on 13.02: Death=(true)

bel · jb.0d01.wtf

OnePS was real, but it was not the solution.

I'm writing this because the project promised a result either way, and the result went the other way. A negative result is still a result. The next person who tries to port this chain to 13.04 or 13.52 needs to know what's structural and what's a knob, and the fastest way to give them that is to write it down while it's still fresh.

Below: the two walls, the functions that were misidentified on the way, what actually survived, and the state of 13.02 as of now.

The question, answered

Does pru_bind copy the sockaddr, or retain a pointer to it?

It copies. The function was resolved against the 13.52 kernel dump, where the tcp6_usrreqs table sits at 0xffffffff83c2fcd8 and the pru_bind slot at +0x18 points at FUN_ffffffff822c9fa0. That function is tcp6_usr_bind.

tcp6_usr_bind reads the sockaddr's fields directly from the user pointer — sa_len, sa_family, the port, the address bytes — with no sockargs intermediary. It then passes the raw user pointer to in6_pcbbind, which is FUN_ffffffff824c8b00.

in6_pcbbind reads the sockaddr's fields again and copies the address and port values into the inpcb at +0xc4, +0xc6, +0xd4, +0xe4. After bind() returns, no kernel structure holds a pointer to the user's sockaddr. Freeing it does not leave a dangling reference.

The premise of the chain was false. Everything downstream of the premise — the SSV primitive, the ROP into libkernel, the allproc walk, the pr_usrreqs dereference — was machinery built to reach one function's disassembly. That disassembly says the vulnerability isn't there.

The divergence from stock FreeBSD

Stock FreeBSD 9's tcp_usr_bind calls sockargs, which copyins the user sockaddr into a kernel mbuf. The PCB-level bind handler then reads from the mbuf, never from the user pointer. That's the design that makes the syscall TOCTOU-free.

PS4's tcp6_usr_bind does not call sockargs. It reads the user pointer directly, then hands that pointer to in6_pcbbind, which reads it again. The lifetime question is still answered the same way — nothing retains the pointer after the syscall — but the copyin intermediary is gone. That's a TOCTOU exposure, not a UAF. It requires racing the syscall's user reads against the user's page-table manipulation, and it does not produce a memory-corruption primitive.

The TCP disconnect race is not a UAF

Along the way a second hypothesis emerged from the tcp_usr_disconnect body: so_pcb is re-read after both rwlocks are dropped, then so_pcb + 0x30 is dereferenced and bitwise-OR 4'd. If a concurrent close() freed the inpcb between the lock drop and the re-read, the final write would land on freed memory.

in_pcbdetach settles it. It's FUN_ffffffff82426100: 

void in_pcbdetach(long inp) {
    *(undefined8 *)(*(long *)(inp + 0x58) + 0x18) = 0;   // so->so_pcb = NULL
    *(undefined8 *)(inp + 0x58) = 0;                     // inp->inp_socket = NULL
    return;
}

The null-store happens first. The free path (in_pcbfree, FUN_ffffffff824262b0) runs after tcp_usr_detach returns from in_pcbdetach, in every branch. Any racer that wins the timing window causes the re-read to return NULL, not a dangling pointer. The subsequent *(NULL + 0x30) is a kernel panic, not a UAF.

Pattern A. Null-then-free. It's a crash primitive, not a memory-corruption primitive.

The WebKit wall structural

The chain is bootstrapped on a bug in WebKit's SerializedScriptValue deserializer: a fixed-capacity MemoryMap that fails to track object identities once a threshold is exceeded. If the map overflows, the duplicate entry at outerGraph[2] is allocated fresh instead of reusing outerGraph[1]'s reference. That fresh allocation is what the heap groom turns into a fake JSCell.

On the WebKit build the PS4 reports — AppleWebKit/605.1.15 (KHTML, like Gecko) Version/17.0 Safari/605.1.15 — the deserializer has been rebased. MemoryMap is a HashMap, not a fixed array. There is no fixed capacity, no overflow, no identity loss.

This isn't the SSV being patched in the sense of "the code was removed." The deserializer still allocates fresh cells for duplicate references when it needs to. What it no longer does is mistakenly deduplicate, or mistakenly allocate — the two failure modes the SSV groom relied on. The bytes still alias; they just don't alias here.

Empirically, across hundreds of cold boots and every config ever tried, the chain reaches one of exactly four outcomes: 

ZERO-HEADER-MISS hex=0000...      cell landed in fresh zeros
ZERO-HEADER-MISS hex=<nonzero>   cell landed on real but wrong JSC data
VALIDATION-MISMATCH rw=true-holder=true   cell landed on the pattern, walk started
PRIM-OK                            the one that counts

ZERO-HEADER-MISS and VALIDATION-MISMATCH are both placement misses. They are not "the bug is gone." The bug is present — the deserializer does allocate a fresh cell — but the cell lands somewhere other than the predecessor pattern. The observed per-boot rate is in the 4–13% band. The reference chain on 11.00 hits first try because its carrier is 160 MB and covers the entire heap. On 13.02 the browser's pool caps at ~84 MB, so the pattern covers a fraction of the heap, and the missing beforeCriticalLoad is what would substitute for the missing memory.

If you are seeing NORMAL-CLONE-MISS known-reference-returned=true on every cold boot, that is a different failure — it means the deserializer is deduplicating correctly and no fresh allocation is being produced for the duplicate index. That is the true structural wall. On the builds tested here, the observed failure modes are ZERO-HEADER-MISS and VALIDATION-MISMATCH, which place the failure in the groom, not in the deserializer.

Why beforeCriticalLoad couldn't save it

I was wrong about this one, and it's worth spelling out why.

The README describes beforeCriticalLoad as "the one piece." It's a JSC allocator nudge: allocate N cells of a given shape, drop them, and the freelist head moves so the next JSObject allocation lands on the predecessor's fakeAddress pattern. That's what makes the difference between a 4–13% per-boot rate and something closer to 100%.

But the nudge operates on placement. It assumes the deserializer is about to allocate. On 13.02, it sometimes does and sometimes doesn't. A nudge tuned for the pre-17.0 allocator geometry does not move the freelist in the direction the deserializer is looking. We swept ?nudge= from 1 to 32 against every ?shape= variant. The failure mode never shifted out of the placement-miss band. The nudge is not the missing piece on this WebKit build; the piece it was meant to substitute for is a 160 MB carrier budget that this firmware's browser does not have.

What I got wrong

Several functions were misidentified on the way down. Worth writing down so nobody repeats them.

The mistaken identification of 822c8d10 as the disconnect path is what generated the entire TCP race hypothesis. Once the table was resolved correctly against the standard pr_usrreqs layout and the sibling function bodies, the sequence turned out to be an attach-path state initialization — which is not race-prone, because it runs before any concurrent access is possible.

The table offsets also don't follow stock FreeBSD. pru_detach is at +0x38, but pru_control sits at +0x30 pointing outside the tcp_usrreq.c address range, and slot +0x28 is NULL rather than a connect2 handler. Deriving entries by offset from a single known function doesn't work on this kernel. Read the table, don't compute it.

What survived

Not everything that came out of the project was a wall. The durable contributions:

The ALLPROC correction

0x01CA8538, not the widely-published 0x01B28538. Derived from procinit at FUN_0080e2c0. The difference is 0x180000. Every published table I've seen has the wrong value, and this one is confirmed against the 13.02 binary.

The carrier ceiling

slots × 8 + drain × drainsz + slab + pred + holes ≤ 84 MB is the correct budget for the browser's sysmemory pool on 13.02. The derived bound slots ≤ ~9,175,040 matches observation exactly — anything above it OOMs, anything below the coverage floor (slots ≥ (copiedLength - 8) / 4) fails ADDROF-FAIL with source-covered=false. This math holds regardless of what the SSV does.

The ROP harness

The makeCtx/layout/callAddr machinery, the gadget encodings, the stub scanner, and the pr_usrreqs table indexing are all correct for 13.02's WebKit. They're reusable the moment any kernel primitive exists on this firmware. The gadget table alone — 15 entries with byte-level validation — is worth keeping.

The negative results

"The sockaddr is copied" and "the disconnect race null-then-frees" are the two findings that matter. Both independently verified against the kernel binary. Both close entire families of exploit hypotheses. Both save the next person the same weeks of work.

What to do next

If you're porting this chain to 13.04 or later:

  1. Check the WebKit build first. If it's Version/17.0 Safari/605.1.15 or newer, the deserializer has been rebased. The SSV groom is a placement lottery at best. Confirm the failure mode is ZERO-HEADER-MISS or VALIDATION-MISMATCH and not NORMAL-CLONE-MISS known-reference-returned=true before you spend time on the kernel side.
  2. Read the pr_usrreqs table, don't compute it. The 13.02 and 13.52 layouts are non-stock. Deriving entries by offset from a single known function gives wrong answers.
  3. Verify in_pcbdetach's ordering before trusting any race hypothesis. If it nulls so_pcb before freeing, the race is a panic, not a UAF, and it isn't worth the two-thread harness.
  4. Re-derive every offset. The kernel RVAs, the stub table, the WebKit gadgets, and the anchors are all compiled into a specific firmware build. Nothing in ps4_offsets.js ports.
  5. If you have beforeCriticalLoad for 13.02, that's the one piece. It's the difference between a 4–13% placement rate and something usable. Every other knob — slab, pred, sep, slots, drain — is a workaround for its absence.

If you're looking for a fresh angle on 13.02: the three live threads are SSV placement (needs the missing nudge), evf (needs a 12.00 kernel dump), and BD-J (needs hardware). The first is the only one reachable from a browser session. If a 12.00 kernel dump surfaces, k_evf_cv becomes derivable and the race path reopens. Until then, the honest answer is that there's no public route from a browser.
